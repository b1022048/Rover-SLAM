# 變數存活週期（系統介面層）

> **閱讀範圍**：`Examples/Stereo-Inertial/stereo_inertial_euroc.cc` + `src/System.cc` / `include/System.h`
>
> 整理這個範圍內出現的變數「存活週期（lifetime / scope）」：從**最長到最短**分類，並專章說明 `m` 開頭成員變數的生命週期由哪裡定義。
> 行號皆對照原始碼確認。**超出此範圍（Tracking/LocalMapping/LoopClosing 內部）不收錄。**

---

## 0. 速查總表

| 存活週期 | 代表變數 | 出生 → 死亡 |
| -------- | -------- | ----------- |
| 整個程式 | `vstrImageLeft`、`vAcc`、`first_imu`、`SLAM`、`new` 出來的 `mpAtlas`/執行緒 | main 外層宣告 → main 結束 / heap 到程式結束 |
| 一個序列 | `vImuMeas`（內容每幀清）、`t_track` | seq 迴圈內宣告 → 該序列結束 |
| 一幀 | `tframe`、`imLeft` 的像素、`imLeftToFeed`、`Tcw` | frame 迴圈/函式內 → 該幀/該次呼叫結束 |
| 一個 `{ }` 區塊 | `lock`(mMutexMode/Reset)、`lock2`(到函式尾) | 進區塊上鎖 → 出 `}` 自動解鎖 |
| 函式參數 | `strVocFile` → 轉存成員 `mStrVocabularyFilePath` | 建構子內 → 建構子 return 即消失 |

---

## 1️⃣ 整個程式存活（最長）

### (a) main 的資料準備容器
| 變數 | 出處 | 說明 |
| ---- | ---- | ---- |
| `vstrImageLeft` / `vstrImageRight` | `:62-63` | 全部影像路徑，整個程式都要用 |
| `vAcc` / `vGyro` / `vTimestampsImu` | `:65-66` | 全部 IMU 資料 |
| `first_imu` | `:69` | **持久游標**：跨幀累進、不每幀重置，所以放最外層 |
| `vTimesTrack` | `:132` | 全程的耗時統計 |

> 這些宣告在 main 最外層，因為要存放**所有序列的所有資料**，活到程式結束。

### (b) `SLAM` 物件
```cpp
ORB_SLAM3::System SLAM(...);   // stereo_inertial_euroc.cc:139
```
- 在 main 的 **stack** 上，從 `:139` 建立到 main 的 `}`（`:248`）為止。
- 離開作用域 → 自動呼叫 System 解構子。

### (c) System 建構子裡 `new` 出來的物件（heap）
```cpp
mpAtlas = new Atlas(0);              // System.cc:154
mpTracker = new Tracking(...);       // :222
mptLocalMapping = new thread(...);   // :229
```
- **關鍵**：`new` 物件的存活週期**不綁建構子作用域**。建構子早就 return，物件仍活在 heap，直到被 `delete` 或程式結束。
- 這就是三條背景執行緒能在建構子結束後繼續跑的原因。

## 2️⃣ 一個「序列(sequence)」存活

### ⭐ `vImuMeas`（物件存活 ≠ 內容存活）
```cpp
for (seq = 0; seq<num_seq; seq++) {
    vector<ORB_SLAM3::IMU::Point> vImuMeas;   // :145  宣告在 seq 迴圈內、frame 迴圈外
    for(int ni=0; ...) {                       // :151
        vImuMeas.clear();                      // :174  每幀清空，但物件不重建
        ...
        SLAM.TrackStereo(..., vImuMeas);       // :192
    }
}  // ← vImuMeas 在一個序列結束才銷毀
```
- **存活週期 = 一個序列**；**內容週期 = 一幀**（每幀 `clear()`）。
- 宣告放 frame 迴圈外 → 重用同一塊記憶體，避免每幀重新配置，是效能考量。

### `t_rect / t_resize / t_track`
```cpp
double t_track = 0.f;   // :148  宣告在 seq 迴圈內，每序列歸零
```

## 3️⃣ 一幀(frame) / 一次函式呼叫存活

| 變數 | 出處 | 說明 |
| ---- | ---- | ---- |
| `tframe` | `:171` | 宣告在 frame 迴圈內，每幀重生 |
| `ni` / `proccIm` | `:151` | for 控制變數，每次迭代更新 |
| `imLeftToFeed` / `imRightToFeed` | `System.cc:291` | TrackStereo 區域變數，每次呼叫生滅 |
| `Tcw` | `System.cc:354` | 追蹤回傳的位姿，回傳後區域變數消滅 |

### ⭐ 特殊：`imLeft / imRight` 的 cv::Mat 引用計數
```cpp
cv::Mat imLeft, imRight;          // :141  宣告在迴圈外（物件活整個序列迴圈）
for(...) {
    imLeft = cv::imread(...);     // :154  每幀重新賦值
}
```
- 物件 `imLeft` 活很久，但它指向的**像素資料**每幀換一份。
- `cv::Mat` 是引用計數標頭，重新賦值會自動釋放上一幀像素——**物件存活週期與資料存活週期分離**。

## 4️⃣ 一個 `{ }` 區塊存活（RAII 鎖，最短且最重要）

`System::TrackStereo` 內：
```cpp
{
    unique_lock<mutex> lock(mMutexMode);   // System.cc:312
    ... 檢查模式切換 ...
}   // ← lock 在此 } 銷毀，mMutexMode 自動解鎖

{
    unique_lock<mutex> lock(mMutexReset);  // System.cc:336
    ... 檢查重置 ...
}   // ← 出 } 自動解鎖
```
- **RAII**：`unique_lock` 存活週期 = 那對 `{ }`。建構時上鎖、解構（離開區塊）時自動解鎖。
- 用 `{ }` **刻意縮短鎖的存活時間**，只鎖要保護的那幾行。

函式尾端：
```cpp
unique_lock<mutex> lock2(mMutexState);   // 註解：「return Tcw之後就會解鎖」
mTrackingState = mpTracker->mState;
...
return Tcw;                              // lock2 在函式結束才解構、解鎖
```
- `lock2` 無額外 `{ }`，存活週期 = **到函式結束**。

## 5️⃣ 函式參數 vs 成員變數（成員存在的理由）

```cpp
System::System(const string &strVocFile, ...) {   // System.cc:50
    mStrVocabularyFilePath = strVocFile;          // :118
}
```
| 變數 | 存活週期 |
| ---- | -------- |
| `strVocFile`（參數） | **只活在建構子內**，return 即消失 |
| `mStrVocabularyFilePath`（成員） | 跟 System 物件一起活，全程可用 |

> 把短命的參數「存進」長命的成員，這正是成員變數存在的根本理由。

## 6️⃣  專章：`m` 開頭成員變數的生命週期「在哪裡定義」

「加 `m` 的變數」＝ **member variable（成員變數）**。它們**沒有自己獨立的生命週期，而是綁在 `SLAM` 物件身上**。由**三個位置**共同決定：

### (1) 宣告為「成員」→ `System.h:196`（`private:`）之後
```cpp
class System {            // System.h:84
    ...
private:                  // System.h:196
    eSensor mSensor;                    // :204
    Atlas* mpAtlas;                     // :214
    Tracking* mpTracker;                // :219
    bool mbReset;                       // :242
    string mStrVocabularyFilePath;      // :263
};
```
> 因為宣告在 class 內（不是函式內），編譯器才知道它們是「成員」，生命週期要跟物件走。

### (2) 出生 → `SLAM` 被建立時（`main:139` → 建構子 `System.cc:50`）
```cpp
ORB_SLAM3::System SLAM(...);   // stereo_inertial_euroc.cc:139
```
- 這行執行，`SLAM` 誕生，所有 `m` 成員同時被配置，由建構子（`System.cc:50`）初始化
  （初始化列表 `mSensor(sensor)...` + 函式體賦值如 `:118`）。

### (3) 死亡 → `SLAM` 離開 main 作用域（`main:248` 的 `}`）
```cpp
int main(...) {
    ORB_SLAM3::System SLAM(...);   // :139  出生
    ...
    SLAM.Shutdown();               // :230  只停執行緒，未銷毀物件
    return 0;                      // :247
}                                  // :248  SLAM 離開作用域 → 所有 m 成員依相反順序銷毀
```
- `SLAM` 在 stack 上，main 的 `}` 一到就自動解構。
- System.h **沒有自訂 `~System`**（header 無 `~System` 宣告）→ 由**編譯器自動產生的解構子**銷毀成員。
- `Shutdown()`（`:230`）≠ 銷毀，只是請執行緒停下；真正銷毀在 `}`。

### ⚠️ `mp` 指標成員 vs 它指向的物件
| | 生命週期 | 由誰決定 |
| -- | -------- | -------- |
| **`mpAtlas` 指標本身** | 跟 `SLAM`（main:139 ~ 248） | 成員身分（System.h:214） |
| **`new Atlas` 指向的物件** | heap，活到 `delete` 或程式結束 | `new`/`delete`，不綁作用域 |

> `mpAtlas = new Atlas(0)`（`System.cc:154`）：指標是成員、物件在 heap，兩條生命週期不同。

---

## 7. 一句話總結

> **`m` 成員變數的生命週期 ＝「宣告在 `System.h` class 內（成員身分）」＋「`SLAM` 在 `main:139` 出生、`main:248` 的 `}` 銷毀」。** 它們沒有自己的作用域，完全跟著 `SLAM` 物件走；而 `mp*` 指標指向的 `new` 物件則是另一條獨立的 heap 生命週期。
